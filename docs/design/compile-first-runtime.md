# Compile-first Shen-C runtime

Status: implementation in an isolated worktree, 2026-10-19. Main and v0.3.0
remain the released hybrid implementation. Final qualification and repeated
performance acceptance remain OPEN until the receipts below establish them.

Agreed defaults: system C compiler plus cache; improve compilation time without
requiring cold-start parity; retain loaded modules until process exit.

## Required behavior

The default implementation compiles every executable KLambda form before it
runs. This includes ordinary loaded definitions, top-level expressions, REPL
forms, explicit eval-kl, closures, and rules generated by datatype/Prolog
compilation. The existing kernel and ahead-of-time applications remain native.
Dynamic Shen behavior stays available: eval means compile and run new code;
redefinition, partial application, escaping closures and mutable cycles retain
their semantics.

Compilation errors are reported as errors. There is no automatic interpreter
fallback in this mode. An explicitly selected interpreter can remain useful
as a diagnostic and differential-testing backend. Merely enabling promotion
or setting the hotness threshold to zero does not meet this requirement.

## Reuse the existing compiler

The native-tier work in PR #13, frozen at 2a7c721e, provides runtime module
emission, compiler invocation, ABI-aware caching and shared-object loading.
It is a foundation, not the finished architecture: it accepts defun-only
modules, promotes at later eval-kl entries and deliberately falls back.

Extend the emitter with an expression/module entry that returns an owned
RcValue and executes no interpreter. It must not initialize the kernel again,
print results implicitly or publish synthetic helper names. Native functions
and closures use the same owned/borrowed contracts and optimizations as AOT
code: last-use moves, releases and guarded cons reuse.

Route the CLI's eval-kl through this entry before executing any user form.
Lazy compilation on first call is acceptable only if the function body never
runs interpreted. Extend generated applications as well: a generated app that
uses load or eval-kl must use the compiled backend, rather than reinstalling
the old interpreter through rc_install_eval.

## Semantics that require explicit work

- Top-level expression results and nested defuns must be handled; the existing
  tier's definition-publication callback is insufficient for general forms.
- Mutable vectors, streams and closures embedded in KLambda need rooted runtime
  literal/capture bindings. Recreating them from printed text changes identity
  or fails entirely; unsupported literals cannot trigger an interpreter fallback.
- Publishing definitions must preserve ordering and dynamic binding lookup.
  Batch only across boundaries that do not change observable effects, errors,
  macros, reader state or redefinition during argument evaluation.
- Code must outlive every active frame and escaping closure that uses it.
  Keep modules loaded initially; safe unloading needs an ownership design for
  code modules, independently of ordinary value reference counts.
- Cache keys bind code, literal layout, runtime ABI, emitter, compiler and flags.
  Private-directory checks, malformed objects and concurrent publication require
  explicit controls. Disk cache pruning and resident-code growth are separate
  resource concerns.

## Compiler backend decision

The first available backend is the existing system C compiler plus a disk
cache. This adds a compiler requirement for previously unseen dynamic code;
closed AOT applications should remain usable without a runtime compiler.
A self-contained installation needs an embedded compiler/code generator.
That can share the execution/module contract, but adds a separate dependency
and portability/optimization qualification task.

PR #13 records roughly 19-26 seconds of user CPU for cold partial promotion,
versus roughly 3.8 seconds for its interpreter baseline, on a shared host.
Those exploratory results are not acceptance timings and do not measure a
fully compiled implementation. Batching, emitted code size, optimization level
and cache reuse must be measured; native execution alone does not imply a
lower end-to-end CPU cost.

## Implementation and qualification

1. Add the general expression entry and rooted runtime literal support, with
   focused redefinition, effect/error ordering, closure escape and cycle controls.
2. Add a strict compile-before-execute backend with visible compilation errors;
   verify that a first-call long loop cannot execute interpreted code.
3. Wire both the CLI and generated applications, retaining current public CLI
   commands and C ownership contracts. Make the dependency requirement explicit.
4. Run the complete pinned 43.1 136-test suite with counters asserting zero
   interpreter execution, including generated datatype rules and top-level code.
5. Run default/boxed fatal ASan/UBSan, emitted ownership and metadata controls,
   source compilation, empty-directory CLI, Make/CMake and Linux/macOS CI.
6. Measure cold compilation, warm-cache load, startup and steady execution
   separately, with matched output, artifact identities, CPU and peak RSS.
   Include actual source/typechecking workloads and separately compare AOT apps.
7. Change the default and document it only after these gates pass. Remove claims
   that ordinary loaded source is fully compiled until that evidence exists.
